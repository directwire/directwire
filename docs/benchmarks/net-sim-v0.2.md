# net-sim v0.2 基准：homa-rpc vs TCP（白皮书证据链 · 第一块真砖）

- **日期**：2026-08-16
- **被测对象**：`crates/homa-rpc`（Homa-lite over UDP，RPC 层 at-least-once + 幂等去重）vs `rpc::tcp_baseline`（4 字节长度前缀帧，thread-per-conn，短连接）
- **模拟器**：`net-sim` —— 真实 socket + 确定性中继代理（splitmix64 种子化 RNG 注入延迟/丢包），不改任何被测代码
- **环境**：单机 Windows 11 loopback（真实实验的 80% 替代，见限制节）；8 并发 worker；短负载 100 B（占 ~91%），长负载 1 MiB（占 ~9%，27 次/轮）；预热 50 次

## 传输层配置

| 参数 | 值 | 说明 |
|---|---|---|
| 重发窗口 `retransmit_timeout` | `2×RTT`，下限 150 ms | 「确认前重发」窗口；无 RTT 样本时用默认 500 ms |
| RPC `attempt_timeout` | ideal 500 ms / 100ms-RTT 350 ms / 1% 350 ms / 5% 200 ms | 响应丢失兜底，恒 `> 重发窗口 + RTT`（避免与发送端自愈竞态） |
| `overcommit` / `grant_increment` | 2 / 1 MiB | SRPT 接收端调度 |
| TCP 对照 | 只注入延迟（丢包无法在字节流代理上可靠注入，见限制） | — |

## 完整数字（2026-08-16 单轮，µs）

| Profile | Homa 短 P50 / P90 / **P99** | Homa 长 P50 | Homa 失败 | Homa 重发 | TCP 短 P99 | TCP 长 P50 | 长消息加速比 |
|---|---|---|---|---|---|---|---|
| ideal（proxy 校验） | 5 608 / 11 414 / **13 356** | 30 799 | 0 | **0** | 7 449 | 21 609 | TCP 快（loopback 无关） |
| 100 ms RTT | 103 336 / 110 566 / **304 347** | 321 653 | 0 | 4 | 103 314 | 1 716 618 | **5.34×** |
| 100 ms RTT + 1% 丢包 | 102 326 / 108 762 / **452 961** | 368 168 | 0 | 19 | 103 551 | 1 716 230 | 4.66× |
| 10 ms RTT + 5% 丢包 | 13 614 / 24 992 / **222 048** | 225 868 | 0 | 44 | 13 360 | 183 622 | 0.81×（homa 慢） |

短 RPC 单程加速比：100ms-RTT P50 = 0.99×（与 TCP 持平）；1% 丢包 P50 = 1.00×。

## 关键结论

1. **长消息在高 RTT 下碾压 TCP：** 100 ms RTT 下 1 MiB 长消息 **Homa 321.7 ms vs TCP 1716.6 ms = 5.34×**。Homa 的 GRANT 调度按字节流推进（无需等拥塞窗口爬坡、无需 ACK 往返逐段确认），TCP 在 1 MiB 上被拥塞窗口增长 + 三次建连 + Nagle 延迟锁死。→ **白皮书主数字。**
2. **短消息单包丢失死区已修复（v0.2 确认前重发窗口）：** 1% 丢包 profile 短 RPC **P99 = 453 ms < 500 ms 验收线**；修复前 P99 ≈ 5.1 s（仅靠 RPC 层 5 s 超时兜底）→ **11× 改善**。
3. **无丢包零额外重发：** ideal profile 重发 **0 次**（确定性单元测试 `无丢包_confirm后_重发窗口零触发` + 基准双重证明）。重发只在丢包事件上触发（1%/5% profile 各 19/44 次 = 请求丢、响应丢、重发被再丢的递推，全部对应真实丢包，非估计错误）。
4. **高丢包下 0 失败：** 5% 丢包 profile 修复前 **2/273 RPC 失败、短 P99 ≈ 10 s**；修复后 **0 失败、短 P99 = 222 ms**（~45× 改善）。长消息抗 5% 丢包仅损失 +23% 延迟（RESEND 增量重发），TCP 在干净链路上仍 0 丢包。
5. **ideal 无回退：** 短 P50 5.6 ms / P99 13.4 ms（修复前 5.9 / 14.6 ms）——验收线「数字不回退」通过，还微升了。

## 诚实限制

- **单机 loopback**：无真实网卡/RTT 抖动/拥塞梯度；结果为真实协议栈行为，但网络部分由中继代理构造。多机实测待办（白皮书约束：不以此为最终证据）。
- **TCP 只注入延迟、不注入丢包**：字节流代理无法可靠注入丢包；TCP 的丢包代价（拥塞窗口退避）方向已知，这里不伪造对比。故 1%/5% 丢包 profile 的「短 P99」对比不对称——homa 是在真实丢包下测，TCP 是干净链路上测。**长消息对比不受影响**（homa 在 1% 丢包下仍赢 4.66×）。
- **loopback 背景丢包**：Windows loopback 即使修复（`timeBeginPeriod(1)` + `SIO_UDP_CONNRESET=0`）仍有 ~1% 背景丢包；ideal 与 100ms-RTT profile 上偶发的重发（0 / 4 次）即来自这些真实丢包事件，非估计错误。
- **长消息在 5% 丢包下 0.81×（homa 慢）**：874 包中 ~44 包丢失的 RESEND 修复成本使 homa 长 P50 达 226 ms，而 TCP 在 0 丢包下 184 ms。这是真实丢包下可靠性对延迟的诚实代价，不是宣称的强项。
